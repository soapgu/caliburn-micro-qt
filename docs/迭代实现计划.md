## 1. 迭代方式

每次迭代完成一批可运行、可验证的功能，同时交付**需要的框架能力、example 演示、必要测试和验收记录**。框架新增能力应在同批 example 中使用，验收通过后再进入下一批，不先实现整套框架再补示例；第二批仅演示 QML 原生输入与方法参数，不增加框架类型。

技术基线、模块目标与依赖方向沿用 [模块与项目结构](模块与项目结构.md)：Qt 6.8.3、C++17，`CaliburnMicroQt` / `Caliburn::MicroQt`、`CaliburnExampleModule` 和 `CaliburnExampleApp`。两个模块采用静态库，QML URI 保持 `Caliburn.Micro.Qt 1.0` 与 `CaliburnExample 1.0`；批次编号和模块版本分别记录，URI 的 1.0 不表示六批能力都已实现。

example 已采用 Boost.Ext.DI v1.3.2 构造注入，仅应用装配库私有依赖 DI；框架与业务 VM 不依赖 DI 库。只创建当前批次需要的文件，公共预设不包含个人 Qt 路径。

从第一批起，ShellViewModel / ShellView.qml 始终作为应用入口。Shell 是项目命名约定，不表示第一批就需要 Conductor：先完成一个页面的绑定，再逐批增加生命周期、子页面和导航。

第一版的 ShellView 根对象是 ApplicationWindow，声明 `required property ShellViewModel viewModel`。启动程序直接加载 `qrc:/qt/qml/CaliburnExample/views/ShellView.qml`，创建失败时诊断并非零退出。根 VM 无 QObject 父对象，由 C++ RAII 持有；退出时先销毁引擎和 View，再销毁 VM。

### 页面与 VM 契约

页面采用点击计数示例，只保存一份 C++ 计数状态，初始为 0，上限为 5。

| 页面元素或 VM 成员 | 目标绑定与行为 |
| --- | --- |
| `count` | 只读 int 属性，实际变化发 `countChanged`。 |
| `message` | 根据 count 计算的只读文字属性，使用 countChanged 通知；初始为“已点击 0 次”。 |
| `incrementText` | 常量文字属性，值为“增加”，绑定增加按钮的 text。 |
| 增加按钮 | 普通 Button 显式绑定 enabled: root.viewModel.canIncrement，onClicked 直接调用 root.viewModel.increment()；objectName 仅用于对象标识。 |
| 重置按钮 | text 为“重置”，enabled 显式绑定 root.viewModel.canReset，onClicked 直接调用 root.viewModel.reset()。 |
| `canIncrement` | 可读 bool 属性，count < 5 时成立，结果变化时发对应 NOTIFY。 |
| `canReset` | 可读 bool 属性，count > 0 时成立，结果变化时发对应 NOTIFY。 |
| `increment()` | 公开无参数 Q_INVOKABLE void 方法；条件成立时增加 1。 |
| `reset()` | 公开无参数 Q_INVOKABLE void 方法；条件成立时归零。 |

文字由 QML 属性绑定读取 VM，按钮通过手写 onClicked 直接调用 VM。QML 不维护第二份计数、不直接写 count，也不自行计算业务守卫。VM 方法自身再次检查条件，不依赖按钮禁用来保证上限。

Shell VM 更新 count 使用 `setAndNotify(m_count, value, &ShellViewModel::countChanged)`，message 复用 countChanged；canIncrement/canReset 对比更新前后的 bool 结果后分别通知。基类仅增加构造/析构及此辅助函数，不增加 displayName、业务属性、状态、信号或字符串通知；完整成员和示例见 [ViewModelBase](ViewModelBase.md)。

按钮可用状态使用 QML 原生属性绑定，由 VM 的 NOTIFY 驱动刷新；事件处理器显式调用具体 VM。canIncrement/canReset 是示例业务属性，框架不按方法名推导条件、不反射查找方法或验证参数。方法自身检查业务范围，View 先于其借用的 VM 销毁。完整用法见 [操作与输入绑定](操作与输入绑定.md)。

1.0 不扫描按钮、不提供附加动作属性或默认目标；特殊目标直接在 QML 表达式中引用，可空目标显式处理 null。objectName 仅用于对象标识与测试，派生按钮沿用 Qt 原生属性与信号。

第二批的 `add(int)` 保留 0～5 的计数范围，example 使用正增量；不接受的业务输入由 VM 拒绝且不改变计数；参数由 QML 显式传入，框架不介入调用。键盘使用原生 Keys 事件并在控件处理之后响应，过滤自动重复；不增加输入适配组件。已有 increment/reset 行为继续保留。

第三批历史中，Home 由 Shell 的 QObject 父所有权管理，不与 unique_ptr 同时负责删除；DI 递归创建 Home/Shell，Shell 构造函数接管 Home，并在钩子中显式传播生命周期；main 只初始化、激活和关闭根 Shell，不提前实现 Conductor。加载前登记 Shell → views/ShellView.qml 和 Home → views/HomeView.qml 两个不同映射，C++ 根入口和 QML ViewHost 使用同一份配置。验收覆盖两个对象的生命周期和身份、Home 的单份状态以及宿主替换/清空。

第三批具体契约已实现：Screen 初始化一次，激活和普通停用幂等；关闭条件已对齐 CM，未初始化时跳过，已初始化对象每次关闭都执行钩子，关闭后可重新激活。2026-10-09 生命周期顺序进一步对齐 CM 3.2.0：先提交状态并通知，再执行钩子，异常不回滚已提交状态。Screen/Conductor 不增加逐次线程检查或转换标记，由调用方保证主线程执行，业务钩子及同步通知回调不得重入修改自身生命周期或管理状态。ViewRegistry 按运行时元对象精确匹配，登记有效绝对 URL，同类型同 URL 在冻结前可重复；通过 freeze() 显式冻结，Bootstrapper 在 Configure 成功后调用，查询不修改配置状态，C++ 和各引擎单例共用进程表。ViewHost 在创建完成后同步装配，创建前注入 typed VM，同类型对象替换也重建；借用指针及销毁连接确保 null、目标销毁与各种错误清空内容。宿主不拥有 VM、不调用生命周期。

当前启动由 buildShell 创建 VM 树、登记映射，Bootstrapper 只调用根 Shell.activate() 自动初始化并激活，再注入 Shell、加载根窗口。Shell 先提交自身状态，在激活钩子中通过 Conductor 驱动 Home；父状态通知先于子项转换。退出或根加载失败只停用关闭根 Shell，根先提交非活动状态，再传播子项关闭；随后释放引擎与 View，最后释放 VM 树。此前钩子后提交状态的验收顺序保留为历史，当前契约见 [ScreenViewModel](ScreenViewModel.md)。Home 的所有权与 CppOwnership 由 Conductor 接管时设置。IoC 历史调整见 [IoC 装配验收记录](IoC装配验收记录.md)。Shell 与 Home 的焦点作用域配合 Loader 保留第二批输入；通用焦点恢复与模态管理不在本批。

### 阶段 4B：已实现与验收

以下记录 4B 交付时的单项接口；当前 Shell 组合方式和构造接口已由 4C 接续。

1. 在示例用户模块新增 `CounterService : QObject`，提供 `count()`、`canAdd(int)`、`add(int)`、`reset()` 和 `countChanged()`，不注册为 QML 类型。服务保存唯一计数，初始 0、范围 0～5；先检查剩余额度再相加，非法输入及同值更新不通知。
2. Home 改为构造注入非空 `std::shared_ptr<CounterService>`，移除计数存储，直接读取服务。保留现有属性、文案、increment/reset/add 及守卫行为；服务仍检查业务条件。构造时初始化守卫缓存，不发初始通知；订阅服务变化后先更新守卫缓存，再发出计数与文案通知，仅在守卫结果变化时通知，不缓存计数副本。
3. Shell 改为继承 `Conductor<ScreenViewModel>`，构造注入 `HomeViewModelFactory`，定义为 `std::function<std::unique_ptr<HomeViewModel>()>`。构造时创建并接管初始 Home，不初始化或激活；空工厂、空返回值、接管失败或空服务抛出 std::invalid_argument，工厂自身异常原样传播。
4. 删除 Shell 手写的子生命周期传播。`onActivate()` 仅在 activeItem 为空时通过工厂创建 Home，再调用 Conductor 基类实现；普通停用与关闭使用基类行为。Shell.initialize() 不提前初始化 Home；首次激活才初始化页面。未初始化 Shell 的关闭仍无操作，已初始化 Shell 的关闭清空选择并延迟释放页面。
5. 保留只读 `home` 属性，以 `qobject_cast` 将 activeItem 投影为 Home，通过 `activeItemChanged` 通知，不另存 Home 指针。ShellView 的 ViewHost 改绑 `viewModel.activeItem`，保留界面、生命周期文字及输入行为。
6. 每次 `buildShell()` 创建独立共享服务，接口及 Bootstrapper 启动入口不变。应用装配层使用 Boost.Ext.DI 绑定服务和 Home 工厂；工厂只捕获共享服务，每次调用创建局部注入器，不捕获已销毁的注入器或 Shell。服务无 QObject 父对象，由工厂与 Home 的 shared_ptr 保持寿命；页面由 Conductor 父树持有。详见 [当前装配接口](IoC与应用装配.md#4c-构造接口与模块边界)。

4B 只展示 Home，不加入 Detail、集合型、导航按钮或确认弹窗。普通停用再恢复使用原 Home；关闭再激活创建新 Home，沿用同一服务及计数。当前项意外销毁后清空界面，在下一次 Shell 激活时重建，不在销毁通知中自动导航。所有创建、服务更新及生命周期调用由应用保证在主线程执行，沿用单项 Conductor 现有通知与延迟删除顺序。

### 阶段 4C：已实现与验收

Shell 改为 Conductor<ScreenViewModel>::Collection::OneActive，集合只读、按加入顺序排列。新项以 unique_ptr 接管，已有成员以借用指针选择；切换普通停用并保留旧项。关闭当前项优先选前一项，没有前一项选后一项，空集合留空；关闭非当前项不改变选择。父关闭一次清空并关闭全部成员，意外销毁只移除和清空、不自动导航。接口与通知顺序见 [Conductor](Conductor.md#collectiononeactive4c-已实现)。

#### CM 3.2 回调式请求与同步生命周期

请求入口已经按 CM 3.2.0 迁移为普通命名的 void 方法，回调仅用于守卫/策略许可，不加入请求完成回调或另一套 Async API。立即许可可以在当前调用栈内完成；延后许可先返回，之后继续同步生命周期。关闭拒绝不发送成功关闭通知，deactivated(close=true) 表示实际关闭生命周期正常完成，实际回收仍延后。

完整接口、候选所有权、单次模态约定、自定义策略、通知及异常规则见 [关闭守卫](关闭守卫.md) 与 [Conductor](Conductor.md)。窗口 showDialogAsync 保留 5A 的 QFuture/QPromise，是明确的 Qt 适配差异。

## Parent 与统一 Conductor 协议增量
