编写日期：2026-11-12。框架源码基线：`00b72ae`。

本文承接前一轮讨论的框架改造方案，范围为 **F1：框架兼容扩展，以及 F2：旧应用兼容验证**。步骤 1 的旧行为基线及步骤 2 的解析契约已实现并完成本机验收；其余新增接口和接入步骤仍为待实施设计。步骤 2 尚未接入 Bootstrapper 或窗口服务，不代表 F1、F2 已整体完成。

相关资料：当前装配方式见 [IoC 与应用装配](IoC与应用装配.md)，启动契约见 [Bootstrapper](Bootstrapper.md)，窗口职责见 [WindowManager](WindowManager.md)。应用侧需求来源为 `/Users/guhui/GitLabs/project_expo/red-conf-system/docs/IoC与CM3.2.0对照评估.md`；本文可独立作为框架实施依据。

## 一、目标与职责边界

采用“框架提供容器无关契约，应用提供具体容器与注册配置”的分层方式。保留已有根工厂路径，同时允许新应用配置实例提供器，由框架取得应用登记的窗口服务，并按需创建根 VM。

| 层次 | 职责 |
| --- | --- |
| Qt 框架 | 定义解析与所有权契约，提供 Bootstrapper 接入、默认窗口服务及启动退出协调 |
| 应用容器适配器 | 对接具体容器，实现类型／名称解析、共享与独占创建、集合及依赖诊断 |
| 应用组合层 | 登记服务、VM、业务工厂，选择真实或模拟实现，管理应用范围资源 |
| 业务 VM 与 View | VM 接收服务和强类型工厂；View 沿用 ViewHost、ViewLocator 与窗口服务装配 |

框架不依赖 Boost.DI，不包含红厅业务类型，不承担自动构造反射、业务注册、运行时参数推导或 MEF 式程序集扫描。首版不增加进程级全局 IoC 状态，使用 Bootstrapper 持有的实例上下文。

不改变 ViewHost、ViewLocator、QML 强类型注入及 Conductor 的职责；不要求业务使用全局服务定位器。应用 VM 迁移、Shell 构造精简、全部弹窗工厂替换均留到后续。

主要改造位置：

- [BootstrapperBase.h](../modules/Caliburn/Micro/Qt/include/CaliburnMicroQt/BootstrapperBase.h)
- [BootstrapperBase.cpp](../modules/Caliburn/Micro/Qt/src/BootstrapperBase.cpp)

当前 `initialize()` 在 `configure()` 前创建具体 `WindowManager`，Bootstrapper 持有 `shared_ptr<WindowManager>`。旧根工厂接收 `shared_ptr<IWindowManager>` 并返回独占根对象，内部统一保存为 `unique_ptr<QObject>`。根显示入口保留具体 `T*` 的 QVariant，用于 QML 注入。

窗口清理所需的 `prepareForShutdown()`、`releaseWindows()` 和 `windowCleanupFailed` 属于具体 WindowManager。仅把成员改成 `shared_ptr<IWindowManager>` 会丢失退出协调能力，必须同步设计生命周期契约。

## 三、实例提供器与强类型访问层

`IInstanceProvider` 及配套访问层已落地，公开头文件为 `CaliburnMicroQt/IInstanceProvider.h`。当前 API、适配边界与验证结果见 [IoC解析契约验收记录](验收/IoC解析契约验收记录.md)。后续 Bootstrapper 和窗口生命周期接入仍按下一节设计推进。

| 当前能力 | 语义 |
| --- | --- |
| `resolve<T>(name)` | 必需共享实例解析；未注册或解析失败明确报告 |
| `tryResolve<T>(name)` | 可选查询；仅未注册可返回空，类型错误、创建失败等仍报错 |
| `create<T>(name)` | 独占创建，并将所有权转移给调用者 |
| `resolveAll<T>()` | 返回指定契约全部实现；未注册返回空集合 |
| `buildUp<T>(object)` | 对已有对象执行适配器声明的注入，不转移所有权 |

### 类型与所有权约束

1. 类型身份使用 C++ 类型标识，名称只用于补充区分同一契约。支持非 QObject 的普通 C++ 服务，不能把类名字符串或裸 QObject 指针作为通用解析协议。
2. 类型擦除结果保留契约类型、所有权和正确析构方式。接口转换由适配器显式完成，不允许从 `void*` 任意强转；应覆盖多重继承导致接口地址偏移的情况。
3. 共享解析保留共享控制块；独占创建返回可安全转移的独占结果。禁止将已有共享实例或借用对象包装成 `unique_ptr`。
4. `buildUp` 仅处理显式声明的注入点，不自动扫描全部 Q_PROPERTY，也不改变对象释放责任。
5. 单实例契约的重复登记必须明确报错；多实现注册与单实例重复分开定义。集合包含全部命名及未命名登记，按登记顺序返回，不按实例指针去重；当前不提供名称筛选。
6. 不支持的能力必须显式报告，不能以空对象、空集合或无操作伪装成功。

### 错误模型与上下文

统一区分未注册、类型不匹配、重复契约、循环依赖、不支持能力及创建失败。诊断至少能定位请求类型、可选名称和失败原因；适配器提供依赖链，框架保留并报告。可选查询不能吞掉真正的配置错误。

Bootstrapper 持有提供器或其受控上下文，生命周期覆盖框架解析和已接入工厂的使用期。首版不建立全局静态绑定；连续创建 Bootstrapper 不得访问前一上下文的容器。仍须遵守现有 ViewLocator 进程级状态的测试隔离规则，不能把提供器隔离等同于所有框架注册状态均已隔离。

### 当前适配协议

公开方法为 `resolve<T>`、`tryResolve<T>`、`create<T>`、`resolveAll<T>` 和 `buildUp<T>(T&)`。名称使用区分大小写、未经修剪的 QString；空名称表示未命名契约。返回结果分别为共享指针、`OwnedInstance<T>`、共享指针集合或 void。

适配器必须实现 `resolveShared`，以 nullopt 表示当前契约未登记；其余 `createUnique`、`resolveCollection`、`injectExisting` 默认报告不支持。共享与独占结果分别通过 `SharedInstance::from<Contract>`、`UniqueInstance::from<Contract>` 从强类型智能指针构造。实例提供器不提供注册 API 或生产容器；重复登记、循环检测、集合顺序由应用适配器保证。

`OwnedInstance<T>` 使用绑定本次创建对象的类型擦除删除器，支持移动、release 和 reset(nullptr)，不得将其 reset 为另一对象或为无关指针复用删除器。后续根对象接入必须保留删除器，不得直接丢弃后包装为默认 unique_ptr<QObject>。已有对象注入通过 `BorrowedInstance::as<T>()` 检查静态契约后访问，不负责动态类型发现。

`InstanceError` 保存错误码、操作、请求与依赖链；普通或未知适配器异常转换为 CreationFailed 并保留嵌套异常，已有 InstanceError 原样传播。接口不提供全局状态或同步保证，QObject 线程规则由应用负责。

## 四、Bootstrapper 可选接入

保留现有构造函数、`configure()`、`onStartup()`、`registerRootFactory<T>()` 和 `displayRootViewFor<T>()` 的调用方式。建议新增配置阶段入口 `setInstanceProvider(...)`，登记时不解析服务。

| 场景 | 窗口服务来源 | 根对象来源 |
| --- | --- | --- |
| 未配置提供器 | 原有默认 WindowManager | 原有根工厂；缺失仍报错 |
| 配置提供器，根类型已登记旧工厂 | 提供器解析 | 旧根工厂优先 |
| 配置提供器，根类型未登记旧工厂 | 提供器解析 | 提供器独占创建 |

具体规则：

- 提供器仅允许在 `configure()` 中登记；配置成功后、进入 `onStartup()` 前解析窗口服务并验证清理能力。
- 未配置提供器时保留原有默认窗口服务创建时序。现有默认服务在 configure 前创建，因此新模式不能简单把全部默认创建无条件延后；实施时明确临时默认实例的释放及失败清理，不能留下两套已投入使用的服务。
- 配置提供器后，解析或能力验证失败即终止启动，不回退默认窗口服务。
- 根类型存在旧工厂时优先使用旧工厂；只有未登记该工厂时才使用提供器。某一路径已选中但返回空、抛异常或结果不合法时直接失败，不切换另一条路径。
- 旧根工厂收到的窗口服务必须是 Bootstrapper 实际显示根窗口所用的同一个实例。应用弹窗也应复用该实例。
- 重复旧根工厂、空工厂、配置阶段限制、单次根显示尝试及单根限制继续沿用已有语义。

根对象仍须无 QObject parent、位于应用主线程。提供器返回后验证实际根类型，不能只相信请求类型标识；验证成功后保留具体 `T*` 的 QVariant 再交给窗口服务。现有 CppOwnership 设置及 Bootstrapper 独占根对象的职责继续保持。

## 五、独立窗口生命周期契约

建议新增 `IWindowManagerLifecycle`，与现有 `IWindowManager` 分离，覆盖以下能力：

| 能力 | 用途 |
| --- | --- |
| 准备退出 | 结束在途弹窗，停止新的窗口交互，解除相应关联 |
| 释放窗口 | 释放桥接、窗口、View、引擎和模型借用 |
| 清理失败通知 | 将失败传递到 Bootstrapper 的退出结果汇总 |

默认 WindowManager 实现该契约，保留原有公开方法和信号。自定义服务可直接实现或提供显式适配器；生命周期控制必须对应实际使用的同一个窗口服务实例，不能单独解析出不相关的清理对象。失败回调的连接与解绑方式在实现时确定，并验证对象销毁后不会回调已失效的 Bootstrapper。

不向旧 IWindowManager 增加纯虚函数，不迫使旧实现为未启用的新入口补方法。启用提供器入口时必须验证生命周期能力，缺失则在启动阶段明确失败。旧路径继续使用原有默认清理机制。

### 退出与失败清理顺序

正常退出与启动失败均按已创建资源执行相应清理：

1. 准备窗口退出，结束弹窗及相关交互。
2. 关闭根生命周期，执行至多一次 `onExit()`；保留现有钩子可访问根 VM 和普通 View 的语义。
3. 释放窗口、View、引擎及模型借用。
4. 释放根 VM 和工厂。
5. 释放窗口服务、生命周期适配器和实例提供器持有的引用。

单个步骤失败不能阻断其他资源释放，继续保留现有非零退出码及清理失败汇总规则。启动失败的 `onExit()` 必须允许部分初始化。应用自行持有的辅助 VM 由应用负责，但不得先于窗口解除借用而销毁。

提供器若持有服务，释放其内部资源也必须遵守上述依赖关系；避免“容器持有单例，单例工厂又强持有容器”的所有权环。注册实例不触发 initialize 或 activate，Screen 生命周期仍由窗口服务、Conductor 和既有所有者协调。

## 七、后续应用试点

F1、F2 验收后，再以红厅应用 `CheckInProgressPageViewModel` 的单个创建器试点。它只依赖稳定共享的 CheckInReader，无子 VM，也无需额外业务参数。

试点仅替换 OutputContentFactory 中该模板的创建器，验证 Boost.DI 适配、既有 Reader 实例身份、独占页面创建及关闭回收。模板选择、ViewHost、Conductor、页面属性和刷新规则保持原有语义；不同时迁移 Shell、其他弹窗或根解析。

后续有运行时参数的弹窗继续采用强类型工厂：调用者提供模式、座位编号等业务值，应用组合层补齐服务。延迟工厂不得捕获已销毁的局部 injector 引用。Shell 的依赖转发与子 VM 组装最后处理，具体应用迁移另立实施批次。
