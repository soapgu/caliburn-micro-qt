## 一、目标与职责边界

采用“框架提供容器无关契约，应用提供具体容器与注册配置”的分层方式。保留已有根工厂路径，同时允许新应用配置实例提供器，由框架取得应用登记的窗口服务，并按需创建根 VM。

| 层次 | 职责 |
| --- | --- |
| Qt 框架 | 定义解析与所有权契约，提供 Bootstrapper 接入、默认窗口服务及启动退出协调 |
| 应用容器适配器 | 对接具体容器，实现类型／名称解析、共享与独占创建、集合及依赖诊断 |
| 应用组合层 | 登记服务、VM、业务工厂，选择真实或模拟实现，管理应用范围资源 |
| 业务 VM 与 View | VM 接收服务和强类型工厂；View 沿用 ViewHost、ViewLocator 与窗口服务装配 |

框架不依赖 Boost.DI，不包含红厅业务类型，不承担自动构造反射、业务注册、运行时参数推导或 MEF 式程序集扫描。F1 首版没有增加进程级全局 IoC 状态；A1 将增加框架 IoC 门面，以受控弱引用访问 Bootstrapper 持有的同一个 Provider，绑定和清理由框架管理。

不改变 ViewHost、ViewLocator、QML 强类型注入及 Conductor 的职责；不要求业务使用全局服务定位器。应用 VM 迁移、Shell 构造精简、全部弹窗工厂替换均留到后续。

窗口清理所需的 `prepareForShutdown()`、`releaseWindows()` 和 `windowCleanupFailed` 属于具体 WindowManager。仅把成员改成 `shared_ptr<IWindowManager>` 会丢失退出协调能力，必须同步设计生命周期契约。

## 三、实例提供器与强类型访问层

`IInstanceProvider` 及配套访问层已落地，公开头文件为 `CaliburnMicroQt/IInstanceProvider.h`。早期解析契约验收见 [历史记录](验收/IoC解析契约验收记录.md)；当前接口收缩见 [实例提供器接口收缩验收记录](验收/实例提供器接口收缩验收记录.md)。Bootstrapper 和窗口生命周期接入已在 F1 完成；新增全局门面与所有权消费链按 [A1 框架设计](A1框架IoC设计.md) 实施。

| 当前能力 | 语义 |
| --- | --- |
| `resolve<T>(name)` | 必需共享实例解析；未注册或解析失败明确报告 |
| `create<T>(name)` | 独占创建，并将所有权转移给调用者 |
| `resolveAll<T>()` | 返回适配器显式提供的契约集合；支持空集合，不扫描单实例登记 |

### 类型与所有权约束

1. 类型身份使用 C++ 类型标识，名称只用于补充区分同一契约。支持非 QObject 的普通 C++ 服务，不能把类名字符串或裸 QObject 指针作为通用解析协议。
2. 类型擦除结果保留契约类型、所有权和正确析构方式。接口转换由适配器显式完成，不允许从 `void*` 任意强转；应覆盖多重继承导致接口地址偏移的情况。
3. 共享解析保留共享控制块；独占创建返回可安全转移的独占结果。禁止将已有共享实例或借用对象包装成 `unique_ptr`。
4. 依赖绑定、构造注入和作用域由应用 DI 后端完成；框架不提供已有对象注入或类型登记 API。
5. 集合由适配器显式提供，原样保留顺序和重复项，不扫描或合并命名与未命名的单实例登记；当前不提供名称筛选。
6. 不支持的能力必须显式报告，不能以空对象或空集合伪装成功。

### 错误模型与上下文

统一区分未注册、类型不匹配、重复契约、循环依赖、不支持能力及创建失败。诊断至少能定位请求类型、可选名称和失败原因；适配器提供依赖链，框架保留并报告。框架不生成依赖图或执行循环检测，后端错误原样传播。

Bootstrapper 持有提供器或其受控上下文，生命周期覆盖框架解析和已接入工厂的使用期。F1 未建立全局静态绑定；A1 改为配置成功后发布受控绑定，窗口／模型清理后按绑定身份解除，拒绝覆盖活动上下文；连续创建 Bootstrapper 不得访问前一上下文的容器。仍须遵守现有 ViewLocator 进程级状态的测试隔离规则，不能把提供器隔离等同于所有框架注册状态均已隔离。

### 当前适配协议

公开方法仅为 `resolve<T>`、`create<T>`、`resolveAll<T>`。名称使用区分大小写、未经修剪的 QString；空名称表示未命名契约。A1 当前返回结果分别为共享指针、`std::unique_ptr<T>`、共享指针集合。

适配器必须实现 `resolveShared`，以 nullopt 表示当前契约未登记；`createUnique`、`resolveCollection` 默认报告不支持。共享与独占结果分别通过 `SharedInstance::from<Contract>`、`UniqueInstance::from<Contract>` 从强类型智能指针构造。实例提供器不提供注册 API 或生产容器；集合由适配器直接转发 DI 后端结果；构造依赖解析与循环诊断由具体 DI 后端承担，不要求应用再写一套容器。

A1 已删除 OwnedInstance：独占结果由默认 unique_ptr 持有，跨类型映射要求契约虚析构；内部类型化 RAII holder 保证错误结果回收，不暴露实例删除器。已删除 tryResolve、buildUp 与 BorrowedInstance，这是有意的公开 API 收缩，原调用方需调整。

`InstanceError` 保存错误码、操作、请求与依赖链；普通或未知适配器异常转换为 CreationFailed 并保留嵌套异常，已有 InstanceError 原样传播。接口不提供全局状态或同步保证，QObject 线程规则由应用负责。

## 四、Bootstrapper 可选接入

保留现有构造函数、`configure()`、`onStartup()`、`registerRootFactory<T>()` 和 `displayRootViewFor<T>()` 的调用方式。已新增配置阶段入口 `setInstanceProvider(std::shared_ptr<IInstanceProvider>)`，仅 configure 中设置一次，拒绝空值；登记时不解析服务。实现与验证见 [Bootstrapper 提供器接入验收记录](验收/Bootstrapper提供器接入验收记录.md)。

| 场景 | 窗口服务来源 | 根对象来源 |
| --- | --- | --- |
| 未配置提供器 | 原有默认 WindowManager | 原有根工厂；缺失仍报错 |
| 配置提供器，根类型已登记旧工厂 | 提供器解析 | 旧根工厂优先 |
| 配置提供器，根类型未登记旧工厂 | 提供器解析 | 提供器独占创建 |

具体规则：

- 提供器仅允许在 `configure()` 中登记；配置成功后、进入 `onStartup()` 前解析窗口服务并验证清理能力。
- configure 成功后一次性选择服务：未配置提供器时创建默认 WindowManager，否则只解析提供器服务；configure 返回 false 或抛异常时不创建默认服务。经公开接口及调用点核对，配置阶段不依赖窗口服务，故将默认服务创建时机后移，不再创建及替换临时服务。历史旧行为基线仍记录原始时序。
- 配置提供器后，解析或能力验证失败即终止启动，不回退默认窗口服务。
- 根类型存在旧工厂时优先使用旧工厂；只有未登记该工厂时才使用提供器。某一路径已选中但返回空、抛异常或结果不合法时直接失败，不切换另一条路径。
- 旧根工厂收到的窗口服务必须是 Bootstrapper 实际显示根窗口所用的同一个实例。应用弹窗也应复用该实例。
- 重复旧根工厂、空工厂、配置阶段限制、单次根显示尝试及单根限制继续沿用已有语义。

根对象仍须无 QObject parent、位于应用主线程。旧根工厂的登记和请求类型必须严格对应；框架不额外验证实际 C++ 类型，保留具体 `T*` 的 QVariant 再交给窗口服务。现有 CppOwnership 设置及 Bootstrapper 独占根对象的职责继续保持。

## 五、独立窗口生命周期契约

已新增 `IWindowManagerLifecycle`，与现有 `IWindowManager` 分离，覆盖以下能力：

| 能力 | 用途 |
| --- | --- |
| 准备退出 | 结束在途弹窗、解除现有交互关联，保留普通 View |
| 释放窗口 | 释放桥接、窗口、View、引擎和模型借用 |
| 清理失败通知 | 将失败传递到 Bootstrapper 的退出结果汇总 |

默认 WindowManager 自身实现该契约并声明 Q_INTERFACES，保留原有公开清理方法及 windowCleanupFailed 信号。采用同一服务对象实现两项接口的设计，不引入独立生命周期适配器；后续启动层从实际使用的 IWindowManager 对象通过 qobject_cast<IWindowManagerLifecycle*> 获取能力，不单独解析清理对象。

接口提供 prepareForShutdown、releaseWindows 和 subscribeWindowCleanupFailed。失败订阅绑定 context 寿命，返回可主动断开的连接；空 context、空回调或跨线程 context 返回无效连接。方法及回调均在服务线程执行，回调不得抛异常、销毁服务或重入清理。实现与测试结果见 [窗口生命周期契约验收记录](验收/窗口生命周期契约验收记录.md)。

不向旧 IWindowManager 增加纯虚函数，不迫使旧实现为未启用的新入口补方法。第 4 步提供器入口已验证生命周期能力，缺失则在启动阶段明确失败。Bootstrapper 现在持有 shared_ptr<IWindowManager>，通过同一对象查询的生命周期接口清理并订阅失败，旧路径同样使用该接口，保留既有清理顺序。

### 退出与失败清理顺序

正常退出与启动失败均按已创建资源执行相应清理：

1. 准备窗口退出，结束弹窗及相关交互。
2. 关闭根生命周期，执行至多一次 `onExit()`；保留现有钩子可访问根 VM 和普通 View 的语义。
3. 释放窗口、View、引擎及模型借用。
4. 释放根 VM 和工厂。
5. 释放窗口服务和实例提供器持有的引用。

单个步骤失败不能阻断其他资源释放，继续保留现有非零退出码及清理失败汇总规则。启动失败的 `onExit()` 必须允许部分初始化。应用自行持有的辅助 VM 由应用负责，但不得先于窗口解除借用而销毁。

提供器若持有服务，释放其内部资源也必须遵守上述依赖关系；避免“容器持有单例，单例工厂又强持有容器”的所有权环。注册实例不触发 initialize 或 activate，Screen 生命周期仍由窗口服务、Conductor 和既有所有者协调。
