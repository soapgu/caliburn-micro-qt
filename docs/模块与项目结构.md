# 模块与项目结构

> 状态：前四批与 5A 已实现并完成 macOS arm64 验收；框架包含同步生命周期、Parent/Conductor、视图装配及通用模态弹窗。5B 关闭守卫和第六批仍待实施，麒麟待验证。历史证据见 [4C 记录](4C验收记录.md)，5A 见 [验收记录](5A验收记录.md)。后续类型与目录明确标为“计划新增、尚未实现”。

## 1. 模块划分

项目采用两个独立模块：**通用框架模块**和**示例用户代码模块**。示例另有一个启动程序，负责对象装配和运行；它不算第三个 QML 模块。后续用户应用按相同边界组织自己的代码。

| 单元 | CMake 目标 | QML URI / 版本 | 职责 |
| --- | --- | --- | --- |
| 框架模块 | `CaliburnMicroQt`；公开别名 `Caliburn::MicroQt` | `Caliburn.Micro.Qt 1.0` | 已实现基类、Screen 生命周期、注册表、ViewHost 和单项及集合型 Conductor；5A 弹窗已实现；5B 关闭守卫规划中、未实施、未验证。 |
| 示例用户代码模块 | `CaliburnExampleModule` | `CaliburnExample 1.0` | 已实现 Shell/Home/Detail VM/View、CounterService 及两个页面工厂；主题待后续批次。 |
| 示例装配库 | `CaliburnExampleComposition` | 无独立 QML URI | Boost.Ext.DI 创建 VM 树，设置 CppOwnership，返回根 Shell；只在应用层依赖 DI。 |
| 示例启动程序 | `CaliburnExampleApp` | 无独立 QML URI | AppBootstrapper 配置映射与根工厂，框架 Bootstrapper 统一启动、根窗口加载、生命周期及退出清理；共享服务由装配库创建。 |

框架和用户模块都以静态库为首版构建形式，通过 `qt_add_qml_module` 在各自模块内统一组织 C++ 类型、QML 组件和资源。框架不再拆成分别公开的 C++ 核心模块与 QML 控件模块。[Qt 官方模块组织说明](https://doc.qt.io/qt-6.8/qt-add-qml-module.html)

技术基线沿用 Qt 6.8.3、C++17、CMake。静态库形式指本项目的两个模块，不要求 Qt 本身采用静态构建。

本文描述六批迭代完成后的目标结构，实际新增功能按 [迭代实现计划](迭代实现计划.md) 分批交付。第一版只包括 ViewModelBase、类型化通知辅助和单页面 Shell VM/View，按钮使用手写 QML 绑定；框架与 example 在每批同步完善，不能把完整目标清单当作第一版交付范围。

## 3. 框架模块内容

### C++ 类型

公开 C++ 头文件放在 `include/CaliburnMicroQt/`，实现放在 `src/`，由 `CaliburnMicroQt` 编译提供。目前包含 ViewModelBase、ScreenViewModel、ViewRegistry、BootstrapperBase、IChild / IParent / IConductor、ConductorBase、两种 Conductor 元对象基类和模板。集合型 Conductor 已在 4C 实现，5A 窗口管理/确认类型已实现；下表的 5B 关闭守卫仍为规划目标。ViewHostState 和 DialogHostState 的头文件位于 src，不作为公开 C++ SDK 头文件提供，但两者均为模块公开、可创建的 QML 辅助类型。

注册到公共 QML URI 的命名类型，其属性、可调用方法和信号均纳入公开 QML 契约；源码目录或“内部”注释不能缩小已注册的接口。可创建性、默认值、读写权限与使用协议应同步记录并由 QML 契约测试验证。

| 类型 | 框架职责 |
| --- | --- |
| `ViewModelBase` | QObject 类型基础，提供 protected 类型化 setAndNotify；不新增业务属性、信号或生命周期状态，见 [完整契约](ViewModelBase.md)。 |
| `ScreenViewModel` | 一次初始化、幂等激活与普通停用、已初始化对象可重复关闭；实现 IChild 和只读逻辑 Parent。 |
| `IChild` / `IParent` / `IConductor` | 纯 C++ 逻辑 Parent、子项快照和管理协议；接口不继承 QObject。 |
| `ConductorBase` | 抽象元对象基类，继承 Screen、声明统一接口、提供 Parent 辅助逻辑和激活结果信号。 |
| `ConductorViewModelBase` / `Conductor<T>` | 单项选择，普通停用子项后留存，裸指针恢复；切换关闭旧当前项。getChildren 只枚举当前项。 |
| `ConductorCollectionOneActiveViewModelBase` / `ConductorCollectionOneActive<T>` | 保留多个成员、单个选择，支持已接管成员切换及关闭后的相邻自动选择；别名 Conductor<T>::Collection::OneActive。 |
| `ViewRegistry` | 提供通用类型映射登记和查询入口，不拥有 VM。 |
| `ViewHostState` | 公开、可创建的 QML 辅助类型，保护 VM 借用并验证 View 注入，见 [ViewHost](ViewHost.md#4-借用与所有权)。 |
| `DialogHostState`（5A 已实现） | 公开、可创建的 QML 辅助类型，关联窗口服务并协调弹窗请求释放，见 [WindowManager](WindowManager.md#dialoghoststate公开-qml-宿主协调接口)。 |
| `BootstrapperBase` | 纯 C++ 启动基类，持有根 VM 和引擎，统一配置、启动、生命周期和退出清理；不向 QML 注册。 |
| `ConfirmationRequest`（5A 已实现） | 保存确认文案的值类型，不携带业务操作枚举，不限制窗口管理入口的 VM 类型。 |
| `IWindowManager`（5A 已实现） | 声明接受自定义 VM 的 showDialogAsync 通用模态弹窗入口，使用 QFuture / QPromise 交付异步结果。 |
| `WindowManager`（5A 已实现） | 协调单个当前弹窗请求、临时 VM 生命周期、一次结果和请求失效；弹窗以 QObject 父树持有，服务在应用层以 shared_ptr 持有。 |
| `ConfirmActionViewModel`（5A 已实现） | 提供确认文案及 accept/cancel 操作，不依赖业务会话。 |
| `IGuardClose` / 关闭策略（5B 规划中、未实施） | canClose(callback) 支持立即/延后交付许可，覆盖成员关闭、单项替换及普通停用、父级全部持有项的关闭许可。 |

生命周期基类由 C++ 创建，向 QML 注册为不可创建类型；5A 确认 VM 同样沿用该方式。`ViewRegistry` 提供引擎管理的查询单例。`ConfirmationRequest` 作为 C++ 确认文案参数，不因模块化而变成可创建的 QML 对象。5A 保留窗口 Future 是 Qt 适配差异，CM 3.2 WPF 使用同步 ShowDialog；本项目不引入嵌套事件循环模拟阻塞返回。窗口管理接口和所有权已实现，见 [WindowManager](WindowManager.md)；5B 回调式守卫的签名、回调类型及关闭完成通知仍待设计。

ViewModelBase 同样以 QML_ELEMENT + QML_UNCREATABLE 注册，C++ 可构造，QML 只能引用。其构造函数不设置引擎所有权；应用暴露 VM 前明确设置 CppOwnership。setAndNotify 的模板定义随框架公开头文件提供，派生 VM 仍须声明自己的 Q_PROPERTY / NOTIFY，基类不依赖用户类型或 DI 库。

### QML 组件

当前框架已提供 ViewHost；DialogHost 和 ConfirmActionView 已在 5A 实现。按钮仍在用户 View 中手写绑定，1.0 不包含动作装配或输入适配组件。当前框架链接 Qt Core/Qml/Quick/QuickControls2；关闭示例和测试仍可独立构建框架。

| 组件 | 框架职责 |
| --- | --- |
| `ViewHost` | 定位 View，创建前注入唯一 viewModel，处理视觉装配。 |
| `DialogHost`（5A 已实现） | 模态展示、关闭处理、输入隔离和焦点恢复。 |
| `ConfirmActionView`（5A 已实现） | 绑定框架确认 VM，展示文案，通过事件处理器直接调用接受或取消方法。 |

这些组件只引用 Qt 与框架类型。框架不包含示例业务、游戏规则、游戏 VM、业务主题或 Boost.Ext.DI。通用确认 View 使用 Qt Quick Controls 的基础样式，应用主题留在用户模块。

生命周期和所有权独立：Screen 关闭不自动删除；Conductor 显式关闭移除记录、清空逻辑 Parent，通知选择后关闭并 deleteLater。单项子项普通停用清空选择、保留 VM 和 Parent；父普通停用保留选择，已初始化父关闭清理全部当前及留存项。集合内切换保留成员，getChildren 枚举全部成员；单项只枚举当前项。View 只借用 VM，详见 [Conductor](Conductor.md)、[Screen](ScreenViewModel.md) 与 [ViewHost](ViewHost.md)。

5A 重置确认已实现并完成本机验收；5B 退出确认/关闭守卫为规划中、未实施、未验证。5B 未来按 CM 3.2 迁移为普通命名的 void 请求入口和回调式守卫，保留同步生命周期；当前同步 bool 接口未改动。单项成员普通停用也检查守卫，集合型普通停用及内部切换不检查；父级普通停用不因此增加检查。父级关闭许可覆盖全部持有项，包括单项留存项。许可未通过前不改变成员、Parent、选择或 View，具体方向见 [第五批阶段划分](迭代实现计划.md#第五批阶段划分)。

## 4. 示例用户代码模块与启动程序

`CaliburnExampleModule` 从第一批起以 ShellViewModel / ShellView.qml 为应用入口，按批次逐步完善，最终包含 Home 首页、Detail 详情及确认交互，展示框架连接方式，不复制贪吃蛇规则。Shell 是本项目的入口命名约定，能力仍按以下批次加入：

| 批次 | 用户模块与启动方式演进（前四批及 5A 已实现，5B 和第六批为规划） |
| --- | --- |
| 第一批 | 只包含继承 ViewModelBase 的 ShellViewModel 和一个 ShellView 根窗口，展示文字与增加/重置按钮；启动程序直接加载资源并注入 VM。 |
| 第二批 | 已实现 add(int)、canAddTwo、“加 2”按钮、数字键 2 与文本框焦点演示，直接调用 VM，不新增框架类型或业务页面。 |
| 第三批（历史） | Shell 演进为 Screen，新增 Home Screen 与 Item 计数页；计数、文案、参数操作和守卫从 Shell 整体移入 Home。Shell 的 ViewHost 绑定 `viewModel.home`，登记根与子页面映射。 |
| 第四批 4A（历史） | 单项 Conductor 核心与测试完成，当时 Shell/Home 示例保持第三批实现。 |
| 第四批 4B（已实现） | Shell 先接入单项 Conductor，宿主改绑 `viewModel.activeItem`；新增共享计数服务及 Home 工厂，关闭后重建页面保留计数。 |
| 第四批 4C（已实现） | 完善 Collection.OneActive 并调整 Shell；新增 Detail VM/View，Home 常驻，Detail 按需创建及返回后释放。 |
| 第五批 5A（已实现） | 框架在 Shell 根窗口加载后自动挂载 DialogHost，引用 IWindowManager / WindowManager 和确认 VM/View，为 Home 重置加入确认；支持自定义弹窗 VM。 |
| 第五批 5B（规划中、未实施） | Detail 返回通过回调式守卫确认；覆盖成员关闭、单项替换及普通停用、父级全部持有项的关闭许可，根窗口退出衔接留待后续。 |
| 第六批 | 保留 Shell 入口，补充独立消费工程与目标平台验收。 |

业务 View 声明明确类型的 `required property XxxViewModel viewModel`。属性、通知、方法和可用条件在用户 VM 中实现，View 显式绑定 enabled 并直接调用方法；用户模块不复制框架基类或通用组件。

`CaliburnExampleApp` 的 `app/` 随批次完善以下职责：

- 第一批只创建根 Shell VM，通过 QML 引擎初始属性注入后直接加载 `qrc:/qt/qml/CaliburnExample/views/ShellView.qml`；ShellView 声明 `required property ShellViewModel viewModel`，失败时诊断并非零退出。
- 第三批加入 Shell 与 Home 的应用映射登记；后续 IoC 调整采用 buildShell 递归构造 VM 树，Shell 构造函数接管 Home，Shell 钩子显式传播生命周期，Bootstrapper 只驱动根 Shell，AppBootstrapper 配置映射与根工厂，main 只调用 Run。根入口和 ViewHost 共用注册表查询，不保存第二份计数状态。
- 第四批 4B 已由装配层为每个 buildShell 创建独立 CounterService 并绑定 Home 工厂；Shell 先接入单项 Conductor，页面由工厂按需创建，计数事实迁入共享服务。4C 已接入集合型及 Detail 工厂，沿用服务。窗口服务归入框架后由 Bootstrapper 创建并传给装配层，自动挂载 DialogHost，注册表提供默认确认映射，5B 将用于 Detail 关闭守卫；依赖均通过构造函数注入。
- 第三批退出时关闭根 Shell，由其先关闭 Home；再销毁 QML 引擎与 View、VM 树；后续借用服务最后释放。

示例装配库通过 PRIVATE 链接 Caliburn::BoostDI，使用固定 v1.3.2 单头文件并自动推导业务 VM 构造依赖，依赖源码位于 third_party/boost-di。VM 头文件、框架模块和业务模块不依赖容器；仅框架构建不添加 DI 目标。装配细节见 [IoC 与应用装配](IoC与应用装配.md)，启动契约见 [Bootstrapper](Bootstrapper.md)。Shell 根窗口为 ApplicationWindow，由引擎创建；放进 ViewHost 的页面根对象仍要求为 Item 或其子类。

ShellView 始终是 ApplicationWindow 根窗口。第三批起 Shell 根窗口和 Home 计数页使用独立的 VM/View 映射，避免把同一类型同时登记为窗口和 Item 页面；其演进步骤见 [迭代实现计划](迭代实现计划.md)。

### 4C 实现归属与后续边界

CounterService、Home/Detail VM、两个工厂契约和页面均属于示例用户模块。工厂具体闭包与 Boost.Ext.DI 绑定属于装配库；框架不引用业务类型。Home/Detail 都显式接收同一共享服务，Shell 接收两个可重复调用工厂，宿主绑定 activeItem。

集合型 Conductor 管理页面父关系及 CppOwnership；home/detail 通过集合查找，不重复拥有页面。不同 buildShell 创建独立计数服务，服务只由 shared_ptr 管理。Shell 构造、导航及服务寿命见 [当前装配接口](IoC与应用装配.md#4c-构造接口与模块边界)。

Home VM 常驻，但本轮 View 每次新建。Detail 返回后关闭并延迟释放，当前 View 先于 VM 卸载。View 保留机制列入 [后续版本 ToDoList](后续版本ToDoList.md)；5A 重置确认已实现；5B 退出确认/关闭守卫规划中、未实施、未验证。本轮结果见 [4C 验收记录](4C验收记录.md)。

## 5. 模块依赖、注册与资源

### 编译与 QML 导入

```text
CaliburnExampleApp
    → CaliburnExampleComposition
        → CaliburnExampleModule
            → Caliburn::MicroQt
                → Qt
        → Caliburn::BoostDI（PRIVATE）
```

用户模块在 CMake 中链接框架公开目标，以传递公开头文件和基类依赖。启动程序通过装配库获得用户模块的公开依赖，AppBootstrapper 在 Configure 中使用框架注册表接口，OnStartup 调用 DisplayRootViewFor<ShellViewModel>()。QML 导入与 C++ 链接分别声明，不能仅链接 C++ 库就假定业务 QML 已导入框架类型。

下面是第三批起 Home 子页面的导入与 typed VM 契约，已用于第三批 Home 页面；第一、二批只有 Shell 根窗口：

```qml
import QtQuick
import Caliburn.Micro.Qt 1.0
import CaliburnExample 1.0

Item {
    required property HomeViewModel viewModel
}
```

框架 QML 使用本模块类型，不导入 `CaliburnExample` 或 `QtSnakeLab`。游戏类型、枚举及业务主题由相应用户模块注册。应用模块的类型信息还须声明对框架模块的依赖，使 QML 工具能识别跨模块的 VM 继承关系。

### 应用提供视图映射

本节登记与查询已在第三批实现；第一、二批直接加载固定根窗口资源，5A 已加入框架确认映射。

ViewRegistry 的通用登记入口及 ConfirmActionViewModel 默认映射由框架提供，业务类型与资源地址由应用装配层提供；应用显式映射优先于框架默认映射。C++ 使用 `ViewRegistry::registerView<T>(const QUrl&) -> bool`，要求 T 继承 ViewModelBase；有效绝对 URL 才能登记。相同类型和 URL 在冻结前重复登记成功，冲突保留原映射。Bootstrapper 在 Configure 成功后调用 `ViewRegistry::freeze()`；独立使用时由应用显式冻结。查询不改变冻结状态，按实际元对象精确匹配，不回退基类。

应用在加载 QML 前完成映射配置，第三批登记 Shell → views/ShellView.qml 根窗口与 Home → views/HomeView.qml 子页面，第四批 4C 已增加 Detail 映射，运行展示阶段只查询稳定的表。QML 单例查询与 C++ `ViewRegistry::viewUrl` 使用同一份配置；不能让引擎单例创建时生成另一份空表。5A 框架确认 VM/View 映射由应用在同一初始化流程登记，框架不硬编码用户页面数量。

根入口通过注册表定位窗口；ViewHost 通过注册表定位页面，并在 Loader 创建前注入 viewModel。两条路径共用定位机制，框架无需包含用户类型头文件。VM 的创建、激活、停用和释放继续由 C++ 管理，注册表不参与所有权接管。

### 静态插件与资源

两个模块使用 `qt_add_qml_module` 的静态库形式，保留 Qt 生成的插件、qmldir 和类型注册信息。已生成 `CaliburnMicroQtplugin` 与 `CaliburnExampleModuleplugin` 插件目标，插件类分别为 CaliburnMicroQtPlugin 和 CaliburnExampleModulePlugin。启动程序的两个插件由 Qt 导入扫描链接；QML、Bootstrapper、Dialog 测试的框架插件也由扫描链接，仅显式补充动态 URL 加载所需的示例插件。以上入口均保留 Q_IMPORT_QML_PLUGIN，不能只链接 backing library 后假定注册已保留。[Qt 静态 QML 插件说明](https://doc.qt.io/qt-6.8/qt-add-qml-module.html)

ParentProtocol、Collection、Conductor 三个纯 C++ 测试使用普通 add_executable 并直接链接 Caliburn::MicroQt；它们不加载 QML，避免自动扫描引入不需要的插件后再次传递框架库。示例模块的 DEPENDENCIES TARGET 声明保留模块及工具依赖，其 PUBLIC Caliburn::MicroQt 链接仍负责 C++ 使用要求，两者不能互相替代。清理前后的实际链接命令及验证见 [链接依赖清理验收记录](链接依赖清理验收记录.md)。

构建输出统一放在 build 对应配置的 qml/URI 路径，Qt 执行导入扫描、生成注册代码及资源。QML 测试仅允许 Qt 安装模块与 qrc:/qt/qml 导入，不依赖构建目录的 QML 副本；动态 URL 加载的 Shell、Home 和框架宿主已纳入验证。后续页面继续验证，不能只依赖扫描推测模块已经可用。[Qt 插件导入说明](https://doc.qt.io/qt-6.8/qt-import-qml-plugins.html)

资源统一采用 `RESOURCE_PREFIX=/qt/qml`，显式设置资源别名。资源地址示例（ViewHost、Shell 与 Home 已生成，确认 View 已在 5A 生成）：

| 模块 | 资源别名示例 | 目标 URL 示例 |
| --- | --- | --- |
| 框架：第三批宿主 | `ViewHost.qml` | `qrc:/qt/qml/Caliburn/Micro/Qt/ViewHost.qml` |
| 框架：5A 确认 View（已实现） | `ConfirmActionView.qml` | `qrc:/qt/qml/Caliburn/Micro/Qt/ConfirmActionView.qml` |
| 示例用户模块：第一批起的根窗口 | `views/ShellView.qml` | `qrc:/qt/qml/CaliburnExample/views/ShellView.qml` |
| 示例用户模块：第三批起的子页面 | `views/HomeView.qml` | `qrc:/qt/qml/CaliburnExample/views/HomeView.qml` |

框架 QML 组件使用文件名作为模块根下的资源别名；用户 View 保留 `views/` 别名。源码目录中的 `qml/` 不自动成为 URL 的一部分，文档地址必须与实际 CMake 别名一致。构建时由 Qt 生成 qmldir 与类型信息，不手工维护重复注册清单。

顶层 CMake 已提供 CALIBURN_BUILD_EXAMPLE / CALIBURN_BUILD_TESTS 选项，关闭二者可只构建框架。公共 Presets 不写个人 Qt 路径；本地路径留在不提交的用户配置中。

qt-snake-lab 当前也处于 Qt 源码未实现阶段，以下是对既有目标设计的调整概要，不是已经完成的代码迁移。本轮不修改该仓库；后续接入时同步修订其 README、实现方案与源码结构设计。

- **测试分工**：框架仓库维护通用生命周期、属性通知、视图宿主和弹窗测试；游戏仓库保留规则、会话、设置、业务 VM 测试及页面/确认/输入的模块集成测试。
