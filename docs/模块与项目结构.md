# 模块与项目结构

> 状态：结构设计。本文中的框架模块、示例用户代码模块、启动程序、构建文件和测试目录均为“计划新增、尚未实现”。本轮只完善文档，不创建占位源码，也没有编译、运行或平台验收结果。

## 1. 模块划分

项目采用两个独立模块：**通用框架模块**和**示例用户代码模块**。示例另有一个启动程序，负责对象装配和运行；它不算第三个 QML 模块。后续用户应用按相同边界组织自己的代码。

| 单元 | CMake 目标（待实现） | QML URI / 版本（待实现） | 职责 |
| --- | --- | --- | --- |
| 框架模块 | `CaliburnMicroQt`；公开别名 `Caliburn::MicroQt` | `Caliburn.Micro.Qt 1.0` | 通用生命周期、视图定位、操作绑定和确认弹窗。 |
| 示例用户代码模块 | `CaliburnExampleModule` | `CaliburnExample 1.0` | 示例业务 VM、服务、View 和主题。 |
| 示例启动程序 | `CaliburnExampleApp` | 无独立 QML URI | 创建服务与 VM、登记视图映射、加载根窗口并管理退出次序。 |

框架和用户模块都以静态库为首版构建形式，通过 `qt_add_qml_module` 在各自模块内统一组织 C++ 类型、QML 组件和资源。框架不再拆成分别公开的 C++ 核心模块与 QML 控件模块。[Qt 官方模块组织说明](https://doc.qt.io/qt-6.8/qt-add-qml-module.html)

技术基线沿用 Qt 6.8.3、C++17、CMake。静态库形式指本项目的两个模块，不要求 Qt 本身采用静态构建。

本文描述六批迭代完成后的目标结构，实际新增功能按 [迭代实现计划](迭代实现计划.md) 分批交付。第一版只包括 ViewModelBase、无参数 ActionBinding、ActionButton 和单页面 Home VM/View；框架与 example 在每批同步完善，不能把完整目标清单当作第一版交付范围。

## 3. 框架模块内容

### C++ 类型

公开头文件放在 `include/CaliburnMicroQt/`，实现放在 `src/`，均由 `CaliburnMicroQt` 编译提供。

| 类型 | 框架职责 |
| --- | --- |
| `ViewModelBase` | QObject 展示基类，不持有 View 或服务定位器。 |
| `ScreenViewModel` | 一次初始化、幂等激活与停用，以及属性通知。 |
| `ConductorViewModel` | 接管子 Screen、维护唯一活动项、显式移除与延迟释放。 |
| `ViewRegistry` | 提供通用类型映射登记和查询入口，不拥有 VM。 |
| `ActionBinding` | 检查方法、参数、守卫及通知，执行前再次核对。 |
| `ConfirmationRequest` | 保存确认文案的值类型，不携带业务操作枚举。 |
| `IDialogService` | 声明确认请求、当前弹窗、忙状态与按请求者取消的契约。 |
| `DialogService` | 管理单请求、临时确认 VM、一次结果和异步交付。 |
| `ConfirmActionViewModel` | 提供确认文案及 accept/cancel 操作，不依赖业务会话。 |

生命周期基类和确认 VM 由 C++ 创建，向 QML 注册为不可创建类型；`ActionBinding` 可由 QML 创建；`ViewRegistry` 提供引擎管理的查询单例。`ConfirmationRequest` 用于 C++ 服务请求，不因模块化而变成可创建的 QML 对象。

### QML 组件

| 组件 | 框架职责 |
| --- | --- |
| `ViewHost` | 定位 View，创建前注入唯一 viewModel，处理视觉装配。 |
| `ActionButton` | 将按钮 enabled 和点击连接到 ActionBinding。 |
| `KeyActionBinding` | 适配焦点路径中的按键，复用操作绑定。 |
| `DialogHost` | 模态展示、关闭处理、输入隔离和焦点恢复。 |
| `ConfirmActionView` | 绑定框架确认 VM，展示文案并触发接受或取消。 |

这些组件只引用 Qt 与框架类型。框架不包含示例业务、游戏规则、游戏 VM、业务主题或 Boost.Ext.DI。通用确认 View 使用 Qt Quick Controls 的基础样式，应用主题留在用户模块。

现有生命周期与所有权约定继续适用：关闭 Screen 不自动删除；Conductor 只移除非活动项并安排 `deleteLater()`；View 只借用 VM；操作执行前复核守卫；确认结果异步交付，请求者失效后丢弃回调。详细行为见 [README](../README.md)、[ViewHost](ViewHost.md) 和 [ActionBinding](ActionBinding.md)。

## 4. 示例用户代码模块与启动程序

`CaliburnExampleModule` 按批次逐步完善，最终包含首页、详情及确认交互，展示框架连接方式，不复制贪吃蛇规则：

| 批次 | 用户模块与启动方式演进（全部未实现） |
| --- | --- |
| 第一批 | 只包含继承 ViewModelBase 的 HomeViewModel 和一个 HomeView 根窗口，展示文字与增加/重置按钮；启动程序直接加载资源并注入 VM。 |
| 第二批 | 同页增加参数操作和快捷键，不新增业务页面。 |
| 第三批 | Home 改为 Screen，ViewHost 展示 Item 计数页；增加独立根窗口 VM/View 配对并登记映射。 |
| 第四批 | 根装配演进为 Shell/Conductor，加入 DetailViewModel、详情 View 和共享业务服务，支持按需创建与返回后释放。 |
| 第五批 | 引用框架确认 VM/View 与服务，为重置和离开详情加入异步确认。 |
| 第六批 | 保留可运行 example，补充独立消费工程与目标平台验收。 |

业务 View 声明明确类型的 `required property XxxViewModel viewModel`。属性、通知、操作和守卫在用户 VM 中实现；用户模块不复制框架基类或通用组件。

`CaliburnExampleApp` 的 `app/` 随批次完善以下职责：

- 第一批只创建 Home VM，通过 QML 引擎初始属性注入后直接加载 HomeView 根窗口；失败时诊断并非零退出。
- 第三批加入应用映射登记、Screen 初始化与激活，根入口和 ViewHost 共用注册表查询。
- 第四批显式构造共享业务服务及 Shell/Home/Detail VM，第五批再创建弹窗服务、登记框架确认映射；依赖均通过构造函数注入。
- 先销毁 QML 引擎与 View，再销毁 VM 树，最后释放被借用的服务。

示例默认不引入 DI 库。下游应用可以在装配层使用 Boost.Ext.DI；VM 头文件、框架模块和业务模块不因此依赖容器。根窗口可以是 ApplicationWindow，由引擎创建；放进 ViewHost 的页面根对象仍要求为 Item 或其子类。

第三批起根窗口和计数页使用独立的 VM/View 映射，避免把同一类型同时登记为窗口和 Item 页面；其演进步骤见 [迭代实现计划](迭代实现计划.md)。

## 5. 模块依赖、注册与资源

### 编译与 QML 导入

```text
CaliburnExampleApp
    → CaliburnExampleModule
        → Caliburn::MicroQt
            → Qt
```

用户模块在 CMake 中链接框架公开目标，以传递公开头文件和基类依赖。启动程序链接用户模块，并使用框架装配接口。QML 导入与 C++ 链接分别声明，不能仅链接 C++ 库就假定业务 QML 已导入框架类型。

下面是示例用户页面的导入与 typed VM 契约，仍为待实现设计片段：

```qml
import QtQuick
import Caliburn.Micro.Qt 1.0
import CaliburnExample 1.0

Item {
    required property HomeViewModel viewModel
}
```

框架 QML 使用本模块类型，不导入 `CaliburnExample` 或 `QtSnakeLab`。游戏类型、枚举及业务主题由相应用户模块注册。应用模块的类型信息还须声明对框架模块的依赖，使 QML 工具能识别跨模块的 VM 继承关系。

### 应用提供视图映射

本节是第三批开始实现的目标契约；第一、二批直接加载固定根窗口资源，第五批才加入框架确认映射。

ViewRegistry 的通用登记入口由框架提供，业务类型与资源地址由应用装配层提供。本文规定登记职责和时机，不将未实现的注册函数签名写成现有 API。

应用在加载 QML 前完成映射配置，运行展示阶段只查询稳定的表。QML 单例查询与 C++ `ViewRegistry::viewUrl` 使用同一份配置；不能让引擎单例创建时生成另一份空表。框架确认 VM/View 的映射也由应用在同一初始化流程登记，框架不硬编码用户页面数量。

根入口通过注册表定位窗口；ViewHost 通过注册表定位页面，并在 Loader 创建前注入 viewModel。两条路径共用定位机制，框架无需包含用户类型头文件。VM 的创建、激活、停用和释放继续由 C++ 管理，注册表不参与所有权接管。

### 静态插件与资源

两个模块使用 `qt_add_qml_module` 的静态库形式，保留 Qt 生成的插件、qmldir 和类型注册信息。计划分别使用 `CaliburnMicroQtplugin` 与 `CaliburnExampleModuleplugin` 作为插件目标。启动程序及 QML 测试入口需要完成对应静态插件链接与导入，不能只链接 backing library 后假定注册已保留。[Qt 静态 QML 插件说明](https://doc.qt.io/qt-6.8/qt-add-qml-module.html)

后续构建需配置与 URI 对应的模块输出目录，核对 QML 导入扫描和 `qt_import_qml_plugins` 的处理结果；动态 URL 加载的页面也纳入验证，不能只依赖扫描推测模块已经可用。[Qt 插件导入说明](https://doc.qt.io/qt-6.8/qt-import-qml-plugins.html)

资源统一采用 `RESOURCE_PREFIX=/qt/qml`，显式设置资源别名。目标地址示例（尚未生成资源）：

| 模块 | 资源别名示例 | 目标 URL 示例 |
| --- | --- | --- |
| 框架 | `ConfirmActionView.qml` | `qrc:/qt/qml/Caliburn/Micro/Qt/ConfirmActionView.qml` |
| 示例用户模块 | `views/HomeView.qml` | `qrc:/qt/qml/CaliburnExample/views/HomeView.qml` |

框架的五个 QML 组件使用文件名作为模块根下的资源别名；用户 View 保留 `views/` 别名。源码目录中的 `qml/` 不自动成为 URL 的一部分，文档地址必须与实际 CMake 别名一致。构建时由 Qt 生成 qmldir 与类型信息，不手工维护重复注册清单。

顶层 CMake 计划提供可关闭的示例和测试构建选项，供下游只构建框架。公共 Presets 不写个人 Qt 路径；本地路径留在不提交的用户配置中。

## 6. qt-snake-lab 调整概要

qt-snake-lab 当前也处于 Qt 源码未实现阶段，以下是对既有目标设计的调整概要，不是已经完成的代码迁移。本轮不修改该仓库；后续接入时同步修订其 README、实现方案与源码结构设计。

```text
qt-snake-lab/
├── third_party/caliburn-micro-qt/  # 计划新增、尚未实现：固定版本框架依赖
├── src/                           # 计划新增、尚未实现
│   ├── app/                       # 入口、DI、Game 工厂、映射注册
│   ├── domain/                    # 无 Qt 的游戏规则
│   ├── application/               # 会话与设置服务
│   ├── infrastructure/            # 计时与存储实现
│   └── presentation/              # 游戏 VM、枚举桥接与棋盘模型
├── qml/                           # 计划新增、尚未实现
│   ├── views/                     # 游戏业务 View
│   └── theme/                     # 游戏主题
└── tests/                         # 计划新增、尚未实现：业务及接入测试
```

- **依赖接入**：框架可构建后，固定到明确版本或提交，以源码依赖和 `add_subdirectory` 接入，关闭框架示例与测试构建；不写个人绝对路径，也不依赖移动分支。
- **通用支撑归框架**：原规划的 `presentation/mvvm`、`qml/mvvm` 以及通用 ConfirmAction VM/View 改为引用框架模块。
- **业务展示归用户模块**：保留 `QtSnakeLab 1.0`，统一包含八个业务 VM、GameEnums、BoardCellModel、配对 View 与主题，显式依赖 `Caliburn.Micro.Qt 1.0`。SnakeGame 继续作为无 Qt 的独立规则库；会话、设置和基础设施保持各自分层。
- **映射归应用装配**：原九对映射改为八对游戏业务映射，加一对框架确认映射。业务 View 保留原 `qrc:/qt/qml/QtSnakeLab/views/XxxView.qml` 目标地址；确认 View 使用框架资源地址，业务 VM 不保存 URL。
- **保留游戏装配策略**：Boost.Ext.DI、GameViewModelFactory 及注入 traits 留在游戏 `app/`；Game 按需创建、返回后延迟释放，以及会话/设置通知约定继续适用。
- **测试分工**：框架仓库维护通用生命周期、绑定、视图宿主和弹窗测试；游戏仓库保留规则、会话、设置、业务 VM 测试及页面/确认/输入的模块集成测试。

游戏模块不依赖 `CaliburnExampleModule`，也不通过复制示例代码取得框架能力。
